# 直播工作台推流方案

> 本轮仅记录方案，不修改业务代码、配置结构或现有工作台。后续实施以单阶段验收推进，不将下面的规划当作已具备的能力。

## 1. 目标与接入方式

在现有录屏工作台增加直播推流能力，复用桌面采集、预览和音视频编码，让工作台能够像 OBS 一样，把画面推送到 B 站直播间。

“推流到 B 站客户端”存在两种不同含义，实施前需要明确：

| 路线 | 数据去向 | 本方案安排 |
|---|---|---|
| 直接平台推流 | 工作台 → B 站提供的 RTMP 接收地址 → 直播间 | 推荐首版路线，手动填写地址与推流码 |
| 交给直播姬处理 | 工作台 → 直播姬能够接收的第三方来源 → 直播姬开播 | 独立适配路线，先核实客户端实际入口与协议，不假设和平台地址相同 |

首版暂按第一条路线规划。若最终需要的是直播姬内的素材来源，应在 L0 阶段调整目标，不能把直接平台推流当作已覆盖客户端接入。虚拟摄像头也属于另一种输出方式，不等同于 RTMP 推流，后续单独评估。

平台接入依据：OBS 的官方服务配置包含 Bilibili Live 的 RTMP 接入项，可作为协议选择的参考；实际地址、推流码和可用权限，以当前账号在 B 站官方页面或客户端提供的信息为准，应用不硬编码平台接收域名。[OBS 官方服务配置](https://github.com/obsproject/obs-studio/blob/master/plugins/rtmp-services/data/services.json)

B 站的第三方开播权限和分区限制应在接入时核对，首版不自动获取推流码，也不承诺登录后就具备推流资格。[B 站官方开播权限问题排查指南](https://www.bilibili.com/blackboard/activity-pSrb2KQb6G.html)

## 2. 现有基础与真实缺口

根据当前源码核对：

| 当前模块 | 已有能力 | 本次需要补充 |
|---|---|---|
| `Oran7DesktopCaptureWorker` / `Oran7CaptureFrameConverter` | D3D11 桌面采集、预览、录制转换 | 保持一份采集源，接入新的输出会话 |
| `Oran7RecordingSession` / `Oran7RecordingBackend` | 独立线程准备、运行、停止；MP4 与 WHIP 两种输出 | 新增直播会话及 RTMP 输出策略，隔离网络生命周期 |
| `Oran7VideoEncoder` | H.264 编码、帧队列、包队列、关键帧请求 | 核实直播硬编路径、码率控制和 FLV 所需编码头 |
| `Oran7AudioEncoder` / `Oran7WasapiAudioWorker` | 系统回环音频；MP4 使用 AAC，WHIP 使用 Opus | RTMP 使用 AAC；麦克风与混音另外补齐 |
| `Oran7RecordingFeed` | 单一编码入口及设备、尺寸、代际交接 | 首版互斥复用，双输出阶段再扩展 |
| 工作台底部工具栏 | 录制控制、系统声音开关及音频控件布局 | 增加直播控制和真实推流状态 |
| 凭据存储 | DPAPI 加密、分组引用、原子保存 | 明确加入直播凭据组和日志脱敏规则 |

需要特别避免三个误判：

1. 现有 WHIP 是 WebRTC 推流，不是 B 站 RTMP 输出，不能只更换 URL 就认为兼容。
2. 麦克风开关、系统音量及麦克风音量滑块目前包含 UI 草稿，不能将它们当作已经接入录制后端。现阶段真实音频来源是系统声音回环。
3. 当前视频编码器的 `liveStreaming` 分支会将 MF 的 `hw_encoding` 设为 `0`；不能直接沿用这一分支并宣称直播使用硬件编码，应先拆分传输协议与编码器策略并实测能力。

同时，现有编码器的 `getPacket()` 是消费式出队。录制和推流分别调用它会瓜分数据包，不会得到完整的两份流；双输出必须先有统一分发入口。

源码入口：`src/cpp/Oran7ScreenCapture/`、`src/cpp/Oran7Config/Oran7AppConfig.h`、`src/qml/Components/Oran7GlobalComponents/Oran7RecordingToolbar.qml`。

## 3. 首版范围

首版提供：

- B 站 / 自定义 RTMP 目标，分别填写服务器地址和推流码；首版均为手动配置。
- 复用当前显示器来源与预览，支持独立的直播分辨率、帧率、视频码率。
- H.264 视频与 AAC 系统声音，SDR / BT.709 输出。
- 开始推流、取消连接、停止推流，以及准备中、推流中、失败等状态。
- 显示实际发送码率、编码帧率、持续时间、积压及丢弃统计。
- 设置自动保存；地址及密钥走既有加密存储。

首版暂不包含：自动开播/下播、自动读取推流码、直播间标题/分区修改、多场景编辑、摄像头合成、多平台同时推送、HDR 直播、动态降码率，以及直播同时高画质录制。现有 WHIP 保留，不在本轮顺带改造；陈旧 TCP/Server 模块继续停用。

“开始推流”只说明输出连接与发送流程，不等于已核实直播间对观众上线；“停止推流”也不承诺调用平台下播。平台房间状态与输出连接状态需要分别展示，避免假成功。

## 4. 工作台布局

保持现有左右工具栏和中间预览结构，窄窗口继续横向滚动，不将侧栏移到预览下方。

| 位置 | 内容 |
|---|---|
| 左栏 | 保留显示器、鼠标、采集帧率等来源设置 |
| 中部 | 保留预览；顶部可增加小型“直播未开始 / 推流中”状态标记 |
| 右栏 | 保留本地录制设置，增加“直播推流”设置分组，二者使用独立参数 |
| 底部第一行 | 系统声音与后续麦克风控制；右侧并列放置“开始录制”“开始推流” |
| 底部状态行 | 输出状态、时长、实际码率、帧率、网络积压及错误入口 |

直播设置通过现有圆角设置项与选择浮层呈现：平台、推流地址、推流码、画质预设、分辨率、帧率、码率。推流码默认遮挡，提供主动显示与清除；不以完整 URL 作为状态标题。

延续工作台自身样式 property 与显式传参，不绑定控制下拉 GUI 的 `Oran7MainUiSetting`。所有新增界面文案纳入现有中英文翻译。

首版录制与直播互斥，但预览始终可用。忙状态由后端派生，界面明确提示互斥原因；后续双输出能力完成前，不展示可以同时启动的假入口。

配置策略延续自动保存：选择项即时提交，文本输入有效后防抖保存，失焦补交。区分“输入有效”“已保存”“本次连接验证成功”，保存成功不代表地址一定可推。直播期间禁止直接热改地址、密钥、分辨率、帧率与编码参数，只允许取消或停止后修改；失败不覆盖最近可用运行快照。

## 5. 模块组织与所有权

不新增全局单例，不把推流网络 I/O 塞入 `Oran7MediaClient` 或 QML。建议在现有采集模块下建立 `Live/` 子目录，编译进 EXE。

以下为建议类型名，尚未创建：

| 类型 | 职责 |
|---|---|
| `Oran7LiveSession` | GUI 线程唯一维护推流状态、代际、取消意图和节流后的统计；由现有采集控制器独占 |
| `Oran7LiveBackend` | 工作线程组合采集入口、编码器及输出资源，按 RAII 顺序回收 |
| `Oran7StreamOutput` | 最小输出策略契约：打开、写包、关闭及错误返回；不急于统一已有 WHIP/MP4 |
| `Oran7RtmpPublisher` | 使用现有 FFmpeg 库完成 FLV 封装、RTMP 网络写入、超时与取消 |
| `Oran7LiveConfig` | 具名配置值，不混用既有 `recording.mode` 的数值含义 |

建议链路：

```text
工作台 QML → Client 兼容门面 → ScreenCaptureBridge / Controller
                                  ├─ 当前预览 worker / 共享 Feed
                                  ├─ 原 RecordingSession：MP4 / WHIP
                                  └─ 新 LiveSession：独立工作任务
                                       → H.264 / AAC 编码
                                       → RtmpPublisher → B 站接收端
```

会话与 Publisher 使用 `unique_ptr` 独占；只有跨线程确有共享需求的 Feed、取消控制与数据包引用使用共享所有权。FFmpeg 上下文、包、帧、网络句柄使用 RAII，QObject 借用保持 CppOwnership。任务仅捕获配置值、共享控制和安全回调，不捕获 Client、QML 或采集 worker QObject。

现有 `Oran7RecordingSession` 继续是录制状态权威，新会话只维护直播状态。两者的互斥与共享采集资源占用由控制器协调，QML 不新增第二份 `isStreaming`。启动意图与实际推流成功分开；开始后至少完成输出头写入与首批音视频包提交，才进入发送状态，平台可见性仍另行验证。

## 6. 编码和参数建议

### 已确认的直播画质范围（2026-11-12，暂不实施）

- 直播分辨率、帧率和码率独立于本地录制参数保存、调整；修改直播档位不覆盖本地录制设置，反向亦然。
- 日常/计划默认档：1920×1080 / 60fps。
- 产品上限：2560×1440 / 60fps（本文将用户所述“2K”按此尺寸记录）。这是本项目拟定范围，接收端是否接受仍需实际验证。
- 提供低于日常档的选择；候选包括 1920×1080 / 30fps、1280×720 / 60fps、1280×720 / 30fps，具体列表实施时再定。
- 本地录制的 120/240fps 不沿用到直播输出，直播最高 60fps；仅共享画面来源，采集帧率仍须满足实际输出需求。
- 本次只确认范围并更新文档，不新增控件、配置字段或推流代码，也不设定新的直播码率上限。

### 编码与预设建议

首版以 H.264 + AAC + FLV/RTMP 为兼容基线。OBS 官方格式说明可用于核对 RTMP/FLV 与编码组合，但不能代替当前 B 站账号的参数限制。[OBS 官方音视频格式说明](https://obsproject.com/kb/audio-video-formats-guide/)

下表是本项目待实测的起步预设，不是 B 站官方上限，也不保证所有账号均可采用：

| 预设 | 分辨率 / 帧率 | 视频码率起点 | 描述 |
|---|---|---|---|
| 流畅 | 1280×720 / 30fps | 3 Mbps | 降低上传和编码压力 |
| 均衡 | 1920×1080 / 30fps | 5 Mbps | 适合桌面、讲解与一般内容 |
| 日常 | 1920×1080 / 60fps | 6 Mbps | 计划默认档，复杂游戏仍需评估压缩效果 |
| 高清上限 | 2560×1440 / 60fps | 待验证 | 计划最高档，码率结合接收端与上传条件确定 |

建议初始 AAC 48kHz / 双声道 / 160kbps，关键帧间隔 2 秒，CBR 或受约束码率；均为设计建议，实施时验证 MF 编码器选项是否真实生效。采集帧率不得低于输出帧率；首版默认最高 60fps，高刷新率采集不直接等于高帧率平台输出。

录制常用的 40～60 Mbps 不直接作为直播默认值。UI 显示单位并区分 kbps 与 Mbps，上传带宽预算包含音频及协议开销。以稳定可用上传带宽留出约 30% 余量作为初步经验值，不根据播放页的 NET 延迟推断可用上传能力。

不得将“已请求硬编”当作硬编已生效，需核对编码器实际初始化结果、持续帧率与 CPU 占用。MF 硬编失败时给出可解释错误或明确的软编回退，不静默改变画质档位。NVENC/QSV/AMF 独立直连后续再评估，不作为首版先决条件。

RTMPS 只在本地 FFmpeg 构建和目标端均支持时开放，不把 RTMP 地址自动改成 RTMPS。还需在 L0 核对随项目分发的 FFmpeg 6.0 的 RTMP、FLV、AAC 和 TLS 能力，而非只依据系统另一份 ffmpeg.exe 判断。

## 7. 网络、背压和退出

直播必须避免历史播放链路曾发生的网络等待卡住 GUI：

- 连接、写包、重连与关闭全部在工作线程；GUI 只提交命令。
- 打开连接、写入和关闭均有截止时间和取消标记，使用协议适配的超时与 FFmpeg 中断回调；实际协议是否及时响应取消必须测试，不能仅设置一个选项就宣称可中断。
- 首版即设置队列的包数、字节数和时间跨度上限，避免断网后持续累积到 GB 级内存。初步按约 1 秒缓冲设计，具体上限根据码率与关键帧大小在 L0 固化。
- 不在持有 Feed 锁时编码或进行网络写入，不能让慢网络阻塞桌面预览。
- 不能任意丢掉 H.264 参考帧后继续发送依赖帧；积压超限时清理旧 GOP、请求 IDR，必要时重建输出，音频同步丢弃过期时间段。
- 单调时间轴驱动音视频，分别换算编码器与封装器 time base，处理 DTS/PTS、编码头及 FLV 序列头；禁止靠修改 fps 标签伪造帧率。
- 网络失败返回可读原因，拒绝连接、凭据过期、编码失败、采集失效分开处理；日志只记录脱敏错误与统计。

L1 首版失败即停止并允许手动重试。L2 再加入有限自动重连：建议 1 / 2 / 4 秒退避，连续 3 次失败后进入 Error，持续成功发送一段时间后才清空预算。每轮重新建立封装上下文与序列头，以关键帧恢复；用户停止立即取消重连，旧代际结果不得复活会话。

普通停止异步完成，界面显示 Stopping，不在 GUI 上等待 join 或网络 flush。直播不为了发送完过期包无限等待；应用 shutdown 保留资源安全回收，退出等待上限与不可中断驱动边界必须单独验证。

推流期间先禁止会破坏采集源的显示器/分辨率修改；系统显示变化导致采集失效时明确停止直播。跨采集代际无缝恢复作为后续能力，不能发送旧尺寸帧或继续使用已释放设备。

## 8. 配置与凭据

建议新增独立 `live` 分组，保存平台、画质参数、目标显示名等公开设置；完整服务器 URL、推流码及其签名参数纳入独立直播凭据组，沿用 `Oran7CredentialStore` 和现有原子提交流程。

- 地址与推流码以同一次配置提交配对更新，避免旧地址与新密钥组合。
- 不在普通 JSON、日志、报错、状态栏、截图夹具或测试数据中写入真实推流凭据。
- 加密保存失败时保留旧配置并显示保存失败；若允许本次临时推流，应明确其仅在内存中生效。
- 关闭自动启动：重启应用只恢复设置与预览意图，不自动向平台发送直播内容。
- 原 `recording` 配置、WHIP 凭据与未知字段保持兼容，不复用枚举强行改变旧配置含义。

实施配置改动前，同步更新 [[RUNTIME_STATE - 运行时状态]] 的权威所有者和 [[CREDENTIALS - 凭据加密与迁移]] 的分组说明；当前仅记录建议，不提前变更这些已实施文档的事实表。

## 9. 麦克风与同时录制

### 麦克风

与 [[VOICE - 变声器与麦克风效果链方案]] 共用后续输入与混音能力，不在推流器内部再造一套麦克风服务。

推荐顺序为：真实麦克风设备采集 → 重采样与时钟对齐 → 系统声/人声独立增益与静音 → 混音限幅 → AAC 编码。需要覆盖设备拔出、权限拒绝和音画同步。变声、监听及降噪可以后续增加，不作为纯系统声音推流的阻塞项。未接入前，麦克风 UI 继续明确标注未生效。

### 同时录制

先完成稳定直播，再开放“直播同时保存本地”。新增唯一编码包分发入口，每个输出持有自己的 `AVPacket` 引用与有界队列；网络拥塞不能拖住本地封装，磁盘失败也不能直接停止直播。

同码率同分辨率可共用一次 H.264/AAC 编码；本地需要更高质量时，再拆分编码分支并评估硬编会话和设备开销。不能通过两个消费者竞争当前编码器队列来实现广播，也不能直接让两个会话覆盖单入口 Feed。

## 10. 实施顺序与验收

| 阶段 | 任务 | 完成标准 |
|---|---|---|
| L0 接入核实 | 明确直推平台还是直播姬；核实账号地址入口、实际 FFmpeg 协议、直播硬编与取消能力 | 固化协议、编码参数、互斥规则和队列预算，形成可实施边界 |
| L1 最小直播 | 独立直播会话、RTMP 输出、系统声音、工作台入口、加密配置、统计与手动重试 | 可持续发送到指定接收端，停止不冻结 GUI，录制/预览无回归 |
| L2 稳定性 | 有限重连、IDR 恢复、异常分类、采集失效处理与长时运行 | 断网/弱网/服务器拒绝时内存受控，取消及时，旧会话不复活 |
| L3 人声接入 | 复用 VOICE 基础采集与混音，接通真实增益/静音和电平 | 系统声音与麦克风可以独立控制，人声录入与音画同步通过验收 |
| L4 双输出 | 单次编码分发或独立编码分支、推流与本地录制分别启停 | 慢网络不影响录制，磁盘错误不影响直播，重复启停资源可回收 |
| L5 平台增强（可选） | 核实可用接口后再考虑房间信息、开播/下播、弹幕面板与自动获取推流信息 | 单独评审权限与接口稳定性，不混入首版 |

建议下一次只实施 L0～L1，先验证一条可靠的推流链路；L2 的增强可分期，但队列上限、超时、取消和凭据保护必须随 L1 一起落地。

离线检查采用临时目录、虚构凭据、合成帧与本地接收替身，覆盖：FLV 编码头、音视频时间戳、错误返回、超时取消、快速启停、队列满、旧代际回调、配置加密/失败保存、资源释放与现有 MP4/WHIP 行为。仅进行 Release 构建与隔离检查，不启动真实主程序。

真实平台验收由用户自行启动程序并开始直播：确认直播间画面与声音、30～60 分钟持续输出、断网恢复、CPU/GPU/内存曲线、反复启停，以及停止后预览和本地录制能正常使用。持续写包只能证明发送端运行，必须通过接收端实际观看确认最终可用。
