# 私人漫游与推荐去重实施方案（MUSIC）

> 目标：接入真正的私人漫游／私人 FM，并记住近期已听、主动跳过的歌曲，减少重启或隔天重新筛选同一批推荐的情况。
> 2026-11-05 已实施推荐入口、心动/私人 FM 默认/熟悉/探索以及独立推荐队列。详见 DATAFLOW 的对应记录；近期历史去重和云端反馈仍待实施，下文这些部分的默认值仍为建议值。未调用真实账号接口、未启动主程序。

## 1. 当前问题与边界

目前 UI 所称的“漫游”实际使用 `/weapi/playmode/intelligence/list`，以当前歌曲和喜欢歌单为请求依据，属于心动／智能播放链路。队列只在内存维护，现有“漫游过滤已喜欢歌曲”只排除喜欢模型中的歌曲，没有跨重启的播放／跳过记录。

因此，昨天主动跳过且未点喜欢的歌曲，第二天仍可能进入推荐。更换推荐接口也不能保证服务器不再返回它们，需同时补充客户端去重。

首版范围：

- 保留心动模式，新增私人漫游，默认采用探索取向。
- 对自动推荐统一应用：当前队列去重、已喜欢过滤、近期已听过滤、近期跳过过滤。
- 历史按网易云账号隔离，重启后恢复；保留明确的期限与容量上限。
- 普通“下一首”不等同于“不喜欢”，不自动调用 FM 垃圾桶接口。
- 手动选歌、上一首回听不受推荐过滤拦截。

本期不做：更换登录方式、引入 Node.js 常驻服务、重写搜索/收藏列表、修改本地音乐播放行为、接入私人 DJ 或推荐场景大全。不承诺推荐算法一定理解每次反馈，也不承诺探索模式全部返回未听歌曲。

## 2. 模式与界面约定

| 播放模式 | 处理方式 |
|---|---|
| 0 顺序、1 单曲循环、2 随机 | 保持现有含义 |
| 3 心动模式 | 保留现有编号和请求逻辑，将显示名称明确为“心动” |
| 4 私人漫游 | 2026-11-05 实施为 DEFAULT，独立推荐队列；真实账号接口由用户验收 |
| 5 熟悉、6 探索 | 2026-11-05 实施为 FAMILIAR / EXPLORE，与心动共用取消/预取/过滤/聚焦机制 |

现有模式图标数组、`% 4` 循环、`setMode()` 的 0～3 校验及 `mode == 3` 分支必须一起审计；不能只加一个按钮。已有模式 3 不静默迁移到私人漫游。若当前模式未持久化，本期不顺带增加启动自动播放。

私人漫游拥有独立的推荐播放归属，允许没有当前歌曲时直接发起播放，不借用或覆盖搜索结果模型。用户主动改选本地/搜索列表歌曲时结束旧 FM 会话，保留用户选择和既有列表播放意图；旧推荐结果不能随后抢占。切回心动时仍按现有规则要求有效的歌曲种子。

下拉设置的网易云播放设置增加推荐分组：

- 私人漫游取向：首版只开放“默认”和“探索”，探索为新功能默认值。
- 过滤已喜欢：沿用现有开关值，适用于心动和私人漫游；旧配置键保持兼容，名称可改为“推荐时过滤已喜欢歌曲”。
- 过滤近期已听、过滤近期跳过：首版建议默认开启，分别显示建议期限 7 天、30 天。
- 清空当前账号的近期推荐记录；说明只清本地记录，不撤销云端“不喜欢”。

不把期限、容量、补取次数全部堆进首版 GUI；高级调整可先留在分组配置。相关文案同时提供中文与英文翻译，协议枚举保持原值。

## 3. 接口路线与实施前核实

| 能力 | 已查到的适配路径 | 首版用途 |
|---|---|---|
| 心动推荐 | `/api/playmode/intelligence/list`，项目现走 WEAPI 对应路径 | 保留 |
| 私人 FM／模式选择 | `/api/v1/radio/get`；模式版本含 `mode/subMode/limit` | 新推荐来源 |
| 听歌记录 | 适配项目的 scrobble／播放日志接口 | 后续准确上报真实播放行为 |
| 明确不喜欢 | `/api/radio/trash/add` | 后续独立用户操作，不能代替普通跳过 |

上述来自第三方适配项目，不是网易云公开承诺稳定的开放协议。M0 必须复核认证、请求加密、参数、响应结构、模式是否真正生效以及错误返回；不能仅替换 URL。当前本地 `NcmProtocol` 的 EAPI 仍需核查，若所选请求依赖未实现协议，先明确最小依赖和测试范围，再决定是否继续该阶段。

私人 FM 的请求不再要求当前歌曲 `songId` 或喜欢歌单 ID；登录态仍必需。保留返回中的有效推荐上下文供后续反馈使用，不伪造上下文，不假定它与心动结果完全同构。歌曲统一映射为既有 `Oran7NcmTrackMeta`，缺失信息按现有批量详情策略补齐，歌曲 ID 全程保持 64 位。

接口不可用、模式不支持或认证失败时明确提示；不悄悄改用心动接口，也不自动改成用户未选择的模式。

## 4. 职责与策略组织

```text
QML 播放命令／设置
  → Client 门面
    → PlaybackViewModel：播放意图、推荐队列、上一首历史
      → CloudMusicService：账号/请求代际、网络调度
        → 推荐来源策略：心动 / 私人 FM
        → NcmAsyncHandlers + NcmProtocol
      → 推荐过滤策略：批次/队列去重、喜欢、近期已听、近期跳过
        → RecommendationHistory：当前账号近期记录的唯一权威
```

拟新增的项目自有类型统一使用 `Oran7` 前缀：

| 拟定类型 | 职责与所有权 |
|---|---|
| `Oran7RecommendationProvider` 及心动/FM 实现 | 推荐来源策略，由 CloudMusicService 独占；后台只接收请求值，不捕获服务 QObject |
| `Oran7RecommendationHistory` | Client 以 `unique_ptr` 独占、无 QObject parent、仅 EXE 编译；GUI 线程持有账号索引和修订版本 |
| 现有 `Oran7RoamFilterStrategy` 的扩展 | 组合过滤条件，不为每条策略复制一份喜欢列表或历史 |

不新增全局单例，不把历史塞入 PlaybackState 或 QML JS。历史对象生命周期覆盖借用它的服务/队列，遵守成员声明和逆序析构约束。是否暴露只读记录数量/保存错误由门面或 ViewModel 转发，不直接给 QML 容器修改权限。

来源策略在 GUI 线程生成不可变请求描述，后台不捕获策略裸指针；切换来源或删除策略后，旧任务即使尚在执行也只能持有请求值，结果按账号和请求代际丢弃。

继续使用 `Oran7Async::Group::Network`，保留现有最多两项网络任务并发限制。一个推荐流只允许一个在途补取请求；反馈不挤占当前打开歌曲的关键请求。

## 5. 播放、跳过与过滤语义

| 事件 | 本地记录 | 是否影响当前播放 | 云端行为 |
|---|---|---|---|
| 仅下载到预缓存 | 不记已听/跳过 | 否 | 不伪报播放 |
| 实际聆听达到阈值 | 更新近期已听时间 | 不切断当前歌 | M4 再接真实播放反馈 |
| 用户主动下一首，包括 Ctrl+→ | 当前推荐曲目记近期跳过，随后切歌 | 按原命令切换 | 不自动进垃圾桶 |
| 自动播完进入下一首 | 按真实聆听记录，不记跳过 | 正常推进 | 可在 M4 上报完成 |
| 上一首回听、手动选歌 | 不因历史而拒绝用户选择 | 正常播放 | 按真实播放事实处理 |
| 无版权、解析/打开失败、网络失败 | 不当作用户跳过或不喜欢 | 沿用失败推进 | 不伪报用户偏好 |
| 用户明确点“不喜欢” | 短期排除并显示提交状态 | 按已确定的交互切换 | M4 验证后才提交 FM 垃圾桶 |

已听阈值建议为累计有效播放 30 秒；已知时长不足 60 秒时使用总时长的 50%，未知时长按 30 秒。应累计实际播放推进，暂停、seek 跳跃和准备耗时不得充当聆听时长。每次打开媒体使用独立播放代际/标识，避免退役播放器或迟到回调把记录写到新歌。

普通手动下一首可记录已选中的当前推荐歌曲，即使用户很快跳过；切换模式、停止、退出或改选其他歌曲不自动记“跳过”。记录范围限定为心动/FM 推荐播放会话，首版不把本地文件或普通搜索播放全部纳入推荐历史。

## 6. 高效查重与补取边界

过滤顺序建议为：校验 ID → 本批/待播队列去重 → 已喜欢 → 近期跳过 → 近期已听。命中任一启用条件即排除，仅处理自动推荐待播项，保留当前曲目和可回听历史。

- 喜欢成员查询复用 `Oran7TrackLibrary::isLiked()` 已有哈希索引。
- 历史采用 `QHash<qint64, Entry>`，Entry 保存最近有效播放和跳过的 UTC 时间；判定时读取时间检查期限，不逐曲扫描整份历史。
- 批次及队列身份使用有界 `QSet<qint64>`；每批 M 首平均 O(M)，单曲成员检查平均 O(1)。
- 到期清理在加载、定时维护或批量提交边界执行，不在每首候选歌曲上做 O(N) 全表清理。
- 连续全被过滤的结果累计三批后停止自动补取，提示“暂无符合过滤条件的推荐”；预取失败不打断当前歌，队列耗尽再停止。
- 不通过偷偷关闭过滤或重新塞回跳过歌曲来“补满”；用户可调整开关或明确重试，重试预算重新计算。

喜欢状态尚未就绪时沿用现有加载等待/失败策略，不能把未知列表当成空列表。喜欢变化、过滤设置变化和历史写入后重新过滤未消费缓存，不对当前歌曲做追溯跳切。

## 7. 持久化与账号隔离

推荐设置拟纳入 `player.recommendation` 分组，默认值只来自 `config/default.json`。现有 `player.roam_filter_liked` 保持唯一喜欢过滤值，首版不再复制为另一个新键。沿用 ConfigBinding 和 AppConfig 的校验、保存及未知字段保留机制。

历史不写进每次保存的普通配置大 JSON。建议单独使用 AppDataLocation 下的 `recommendation-history/v1/<账号键>.json`，首版无需引入数据库。账号键来自已确认的网易云 UID，不使用昵称、Cookie 或 Cookie 哈希作为稳定账号标识；文件名可用 UID 摘要，但摘要不等于内容加密。

建议文件只保存：版本、账号标识、歌曲 ID、最近有效播放/跳过 UTC 时间。ID 使用十进制字符串存储，恢复时严格校验为正的 64 位整数。不保存歌曲 URL、Cookie、csrf 或完整响应。每账号最多 10000 项，清理过期项后按最近事件淘汰最旧项；容量限制可能使部分记录提前到期，应在文档中明确。

读取、序列化和写盘不得阻塞 GUI；后台只持不可变快照。使用串行写入与修订序号、`QSaveFile` 原子提交，旧快照不能覆盖新状态。清空记录在同一写入队列提交空快照，提交成功后才报告持久清空成功，不能被在途旧保存复活。

账号切换先失效旧请求与回调，再发布对应账号的历史索引。UID 尚未确认时只使用当前会话内存记录，不能继承上一账号的文件。坏文件先备份再降级，未来版本不可覆盖；磁盘失败仍可播放，但需显示记录未成功保存。退出先冻结新记录并收尾已接受的保存，再进入 Async 总关闭；不持久化带凭据的云端重试任务。

## 8. 云端反馈分期

M1～M3 先确保本地跨天过滤可靠，云端反馈放到 M4，避免首批同时修改推荐、播放统计和账号状态。

- 使用真实播放时长与真实结束原因，区分播完、主动切歌、暂停和失败。
- 每个播放标识只生成一次最终反馈；不确定服务端是否成功时，不盲目重试可能重复计数的非幂等上报。
- 账号代际隔离反馈；退出/换账号后不能把旧账号任务附着到新凭据。
- 明确“不喜欢”使用单独操作，普通跳过只做本地有限期过滤。
- FM 垃圾桶是否可撤销、影响范围及反馈参数须在 M0/M4 核实；不宣称永久或全平台屏蔽。清空本地历史不等于撤销云端偏好。
- 上报失败不阻塞当前播放，避免反馈失败引发无限请求。

## 9. 实施阶段与交付门槛

| 阶段 | 交付 | 验收后才能继续的条件 |
|---|---|---|
| M0 接口验证 | 核实私人 FM 默认/探索请求、登录 UID、加密与响应；补充脱敏样例和解析 fixture | 证明所选协议路径可用，记录限制；真实账号验证由用户进行 |
| M1 私人漫游 | 新增模式 4、推荐来源策略、默认/探索选择、代际取消和有界预取；明确模式 3 名称 | 保持心动/普通模式行为，新 FM 不依赖当前 songId/喜欢歌单 ID |
| M2 跨重启去重 | 历史服务、真实已听/主动跳过记录、期限/容量、账号隔离和原子持久化 | 重启后仍过滤已记录曲目，无账号串用、无旧写入复活 |
| M3 设置与完整验收 | 组合过滤策略、预缓存重筛、清空记录、空结果提示、中英文文案与持久化错误反馈 | 过滤不打断当前曲目、不阻止手动回听，不无限补取 |
| M4 云端反馈 | 真实播放上报；明确“不喜欢”操作及 FM 垃圾桶，按接口验证结果逐项开放 | 无伪报、重复统计或普通跳过误提交垃圾桶 |

建议首轮以 M0～M3 为完整交付目标，M4 单独实施；暂不扩展熟悉、场景、拼图模式。各阶段独立编译、独立验收，文档状态通过后逐项更新，不能用计划条目代表已完成。

## 10. 验证清单

离线检查使用虚构账号、临时目录、替身网络和可控时钟，不读取真实凭据，不启动主程序：

- 默认/探索请求参数、协议错误、空列表、元数据缺失与 64 位歌曲 ID。
- 一万条历史及大型喜欢列表下的批量过滤；性能检查使用相对规模和结构验证，避免脆弱的单机毫秒硬阈值。
- 播放阈值、暂停、seek、自动结束、手动下一首/快捷键、上一首、失败和迟到回调的区别。
- 同批/跨批/待播重复，过滤开关变化、喜欢变化、全过滤三批停止和用户明确重试。
- 7/30 天边界、容量淘汰、重启恢复、清空与在途保存竞态、磁盘失败、坏文件/未来版本。
- A/B 账号切换、UID 未就绪、注销、在途旧请求及云端反馈隔离。
- 0～4 模式校验、图标/循环选择、既有模式 3 兼容、只读 PlaybackState、中文/英文设置。

每阶段只构建 Release，并执行与改动相应的离线检查。真实网易云接口、跨天推荐新鲜度与 UI 操作效果由用户验收；本地过滤命中可以验收，服务端推荐算法效果不作为客户端可保证的结果。
