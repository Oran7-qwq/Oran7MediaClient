# 网易云推荐模式低概率 GUI 卡顿排查

日期：2026-11-17。

用户反馈探索及其他推荐模式在新拉取歌曲时，偶发整个主窗口停顿几十秒后恢复。现场不能立即复现，本次没有取得该次挂起的有效线程栈，因此不能把任何单一环节认定为已证实的唯一根因。

## 调用链与检查结果

- 推荐接口：PlaybackViewModel → CloudMusicService → Oran7Async Network 组 → NcmAsyncHandlers。阻塞 curl 只在网络工作线程执行；后台最多两个任务并行。网络慢可能延迟推荐到达，但这条提交路径没有在 GUI 同步等待请求完成。
- 返回路径：GUI 校验请求和账号代际，过滤/去重并更新推荐模型，再经 trackRequested 选择曲目、持久化、解析播放地址与加载歌词。所有有效推荐模式共用这条路径。
- 播放器退役仍由独立后台任务回收；旧结果不能按新请求消费，未恢复跨线程关闭 FFmpeg I/O 或 GUI join 的旧逻辑。

## 本轮修正

确认原歌词服务的 stop/load 在 GUI 线程同步销毁每轮获取器；获取器又独占 QNetworkAccessManager，因而每次切歌都会同时拆除网络管理器和后端连接。这是共用链路上的同步清理风险，网络异常时尤其不应把后端清理反复放在切歌路径。本次未用真实异常网络复现其几十秒耗时，不将该风险直接等同于现场根因。

默认歌词服务现在独占一个长生命周期 QNetworkAccessManager，每轮获取器借用它，仍单独持有和取消当前 reply。切歌先失效代际、断开旧回复、abort 并排队销毁回复，清理每轮临时目录；切歌不再同步销毁网络管理器。服务退出后才释放管理器；测试用的获取器独占注入方式保持兼容。四个歌词来源请求统一设置 15 秒传输超时，这不是 GUI 等待时长，也不承诺覆盖操作系统 DNS/PAC 的所有阻塞情况。

增加仅超 150ms 才输出的 `[GuiPerf]` 日志，记录阶段和耗时，不记录 URL、Cookie、请求体、响应体：

| stage | 操作范围 |
|---|---|
| recommendation_commit | 推荐结果过滤、模型提交及随后的同步信号链 |
| track_select_and_save | 选择当前曲目与持久化 |
| lyrics_request_reset | 旧歌词请求和临时目录清理 |
| lyrics_request_start | 发起歌词网络请求 |
| lyrics_load | 歌词整体加载入口 |
| playback_toggle | 创建/准备播放器或切换播放状态 |

计时在操作返回后记录。如果仍出现卡顿，应保留恢复后的这些日志，区分网络等待、GUI 结果提交和其他同步环节。未命中这些阶段不代表不存在其他 GUI 阻塞。

## 隔离验证

- policy_checks：逐一将 mode 3/4/5/6 的后台请求用信号量保持未完成，验证 GUI 心跳持续、结果未提前播放，放行后仅收到有效结果；普通模式能退出推荐。原有喜欢过滤、大列表哈希查找、模式替代及旧结果隔离继续回归。
- lyrics_checks：使用生产服务及获取器，只有网络 reply 为替身。连续切换 30 轮，在整个运行期间只创建一个网络管理器，旧请求被取消，等待期间 GUI 心跳运行；只有最新请求发布歌词，stop 不销毁后端，服务析构才释放管理器。
- 回归网易云协议、curl 传输、地址解析、播放控制、推荐 QML 与配置检查。
- 检查不访问真实账号或网络，不启动主程序。当前修改的 Release 生产对象已编译；遵照用户自行构建的安排，不覆盖正在运行的主程序 EXE。

本轮消除了上述重复同步清理风险并补上定位证据入口；原始低概率现场仍需新版本长期使用确认，不能宣称已完全根除。
