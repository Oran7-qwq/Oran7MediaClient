# 网易云切歌等待排查（2026-11-18）

## 现场证据

用户反馈顺序播放与探索模式均可能在切歌时整窗停顿，十几秒后恢复，不崩溃。只对用户已运行实例做采样，未启动、操作或结束主程序。

同一次切歌的日志时间：

| 事件 | 时间 |
|---|---|
| 收到旧播放器暂停请求 | 13:03:19.884 |
| 旧媒体读取线程退出、进入音频关闭 | 13:03:19.997 |
| 网易云播放地址请求成功返回 | 13:03:20.556 |
| 旧音频设备关闭完成 | 13:03:43.096 |
| 新播放器准备完成 | 13:03:43.353 |

播放地址约 650ms 已返回，主要停顿位于旧音频解码退出至设备关闭完成之间，约 23 秒。不能把这段等待全部归因于网易云服务器。

现场主线程采样多数落在 Qt 事件等待，另一次非挂起采样落在显示驱动调用；未取得能直接证明整个 GUI 阻塞原因的完整调用链。以上证据可以定位旧播放器退役异常耗时，不能据此断言每次界面停顿都已归因，更不能宣称此前 1GB 内存占用已解决。

临时采样记录位于 `build/refactor-work/ncm-switch-freeze-20261118/`，无响应检测使用 WM_NULL，初次采样使用非挂起模式；一次补充采样使用非侵入式暂停快照，采样后即退出调试器。没有注入或生成全内存转储。

## 实施修正

原实现由 GUI 调用 `stream_open` 初始化 SDL 子系统，读取线程打开设备，退役线程关闭设备和退出子系统。SDL 2.26.5 的 Windows COM 初始化默认优先 STA；源码要求需要 MTA 的调用方提前初始化。参考 [SDL Windows COM 初始化](https://github.com/libsdl-org/SDL/blob/release-2.26.5/src/core/windows/SDL_windows.c) 与 [WASAPI 设备创建／释放](https://github.com/libsdl-org/SDL/blob/release-2.26.5/src/audio/wasapi/SDL_wasapi.c)。

`Oran7SdlAudioDevice` 现在按需独占一条 MTA 控制线程：

- 同线程执行 SDL init、设备 open/pause/close、SDL quit，最后配对释放 COM。
- GUI 不初始化音频驱动；Native 读取／消息／退役线程通过串行邮箱提交控制命令。
- 每个播放器仍独占设备，旧播放器完全释放后才启动最新目标；不以放弃旧线程、提前销毁缓冲或重复打开设备来绕过等待。
- 保留 F32 优先、S16 回退、音效处理和音量淡入淡出。失败时把线程局部 SDL 错误复制回调用线程。
- 原有关闭规则继续生效：先清空句柄，不持有 SDL 回调锁关闭设备；回调退出后才释放处理器。
- 超过 250ms 的初始化、打开、关闭与退出阶段输出 `[PlaybackAudio] stage=… elapsed_ms=…`，不输出媒体地址、凭据或设备身份。

## 验证与边界

新增合成慢设备检查，验证打开／关闭等待期间 Qt 事件循环能继续推进，所有设备生命周期操作使用同一后台 MTA 线程，失败回退不重复初始化、退出配对归还引用。原真实 SDL dummy 驱动检查继续覆盖并发暂停／关闭、旧 ID、回调收尾和 RAII。

真实 Native／FFmpeg 的慢网络取消、32 次切歌内存与句柄检查，以及视频帧节奏回归通过；同时通过播放控制、地址解析、网络传输和歌词检查。32 轮预热后私有内存约 14.20→14.68MiB，句柄 237→237，仅为隔离测试结果，不代表真实驱动长期内存结论。

Release 源码编译通过，最终链接被运行中的旧 EXE 占用，未结束用户进程。现场 Windows 音频设备与显示驱动的停顿仍需用户更新程序后验收；如果仍发生，可依据新增阶段耗时与下一次线程快照继续定位。没有强杀音频线程、停止用户进程或绕过设备完整释放。
