# ADR-0011：运行时状态的三层模型与"单一所有者"纪律

> 状态：`提议`（目标规范，尚未全量落地）

## 背景

Qt/QML 的双向绑定让"任意一端都能改状态"变得非常容易。本项目实际演化出了三套并存的做法：

1. C++ 私有成员 + 信号广播（`Oran7MediaClient::playProgressUpdated`）；
2. QML 单例自己存（`BasicConfig.isPlaying`、`currentMedia*`）；
3. 持久化文件（`config.json` / `profile-*.json`）。

结果是同一个事实有多份副本：`isPlaying` 只在 QML、深色模式有三份、播放归属有三份、主题状态混进设置状态。表现是"界面不刷新""重启回退""切歌串台"这类难定位的问题，而不是编译错误。

## 决策

把运行时状态显式分成三层，并规定每层只能有一个权威：

| 层 | 权威 | 允许的同步方向 | 例子 |
|---|---|---|---|
| 领域状态 | C++ 对象 | C++ 写 → QML 读（`Q_PROPERTY` + `NOTIFY`）；QML 只能通过 `Q_INVOKABLE` 请求变更 | 播放状态、登录态、抓屏参数、曲库 |
| 界面瞬时状态 | QML | 仅本组件/本页 | 动画进度、hover、弹窗开关 |
| 持久化状态 | 文件 | 启动读、明确保存点写 | 音量、窗口几何、Cookie、主题 profile |

配套规则：

1. **命令下行、状态上行**：QML 不直接改领域状态字段，只发"意图"。
2. **列表一律 `QAbstractListModel`**：不再用"逐条信号 + `ListModel.append`"。
3. **持久化只在生命周期点发生**：启动加载、退出保存、用户显式操作；不做隐式写盘。
4. **C++ 不读 QML**：需要 QML 的几何/状态时由 QML 调 `Q_INVOKABLE` 上报。
5. **一个事实一行**：新增状态必须先在 [[RUNTIME_STATE - 运行时状态]] 的所有权表里登记。

## 后果

### 正面

- 状态相关的 bug 可定位（唯一所有者、唯一通知路径）。
- QML 变成纯投影，巨型组件可以被拆小而不丢状态。
- 持久化格式可以独立演进（schema/version/迁移）。

### 负面 / 代价

- 迁移期需要"双写"（旧信号与新属性并存），否则一次性改完风险太高。
- C++ 侧代码量增加（状态类、模型类），QML 侧减少。
- 需要纪律：任何"图省事直接在 QML 改一下"的提交都会重新制造副本，必须在 review 里挡住。

## 备选方案

1. **保持现状（QML 为主）**：改动最小，但状态继续分裂，且 C++ 侧永远无法闭合状态机（例如暂停态对 C++ 不可见）。
2. **全部状态搬到 C++**：包括动画/hover，会让 QML 失去声明式优势，且跨语言往返开销大。
3. **引入第三方状态管理库**：项目规模不值得，且会与现有单例体系冲突。
