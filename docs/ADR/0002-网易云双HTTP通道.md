# ADR-0002：网易云接口走双 HTTP 通道（QNAM 与系统 curl.exe 并存）

> 状态：`已接受`（实现于 `src/ncm/network/`）

## 背景

网易云（`music.163.com`）对请求做 TLS/HTTP 指纹级的风控。实测用 Qt 的 `QNetworkAccessManager`：

- 带登录态的接口经常返回 **HTTP 200 + 空 body**；
- VIP 歌曲的 `enhance/player/url` 返回 `code:-110`；
- 同一组参数换 Windows 自带 `curl.exe`（Schannel TLS）则正常。

这不是 Cookie 或参数错误，换传输栈就好——属于服务端按指纹做的静默降级。

## 决策

保留两条传输通道，按"是否带登录态/是否写操作/是否限流敏感"选择：

| 通道 | 用在 |
|---|---|
| `CurlHttpClient` / `blockingCurl`（系统 `curl.exe`，`--http1.1 --ssl-no-revoke`） | 登录、账号、播放地址、歌单读写、漫游 |
| 各模块 QNAM（无独立 NCM HttpClient） | 歌词、B 站、ping 与启动详情；当前搜索 handler 使用 blockingCurl |

Cookie 必须手工注入（curl 进程无状态）；写操作 CSRF 同时放表单字段与 query。

## 后果

### 正面

- 登录、VIP 播放、点赞/排序稳定可用。
- 匿名只读仍走 QNAM，避免每个请求 10-30ms 的进程创建开销。

### 负面 / 代价

- **每个请求一个进程**：延迟高、无法复用连接、退出时要等 `waitForFinished(15s)`。
- Cookie 传递靠字符串拼接，`os=pc; appver=8.10.35` 只能给播放地址接口（给 WEAPI 会触发风控）。
- 依赖用户机器上存在 `C:\Windows\System32\curl.exe` 与可用的 Schannel。
- `blockingCurl` 在线程池里是同步阻塞，占线程。

## 备选方案

1. **全用 QNAM + 自定义 TLS**：需要替换 Qt 的网络栈，成本远超收益。
2. **用 libcurl 静态链接**：能解决进程开销与指纹问题，但要引入新的第三方依赖与 TLS 后端配置，且构建复杂度上升（本项目已经为 OpenSSL 付过一次代价）。可列为中期改进。
3. **用 WebView 承载所有请求**：可行但状态同步复杂，且已有 CDP 登录的更重依赖。

## 2026-10-24 实现核对

P1-4 删除无人使用的 HttpClient 包装，并未移除项目中的 QNAM 通道。当前搜索/喜欢/漫游由线程池 blockingCurl 执行；异步 curl 用于账号、写操作与播放 URL。curl 不打印响应体或原始 stderr，临时目录由 RAII 清理。凭据和既有协议参数保持原样。
